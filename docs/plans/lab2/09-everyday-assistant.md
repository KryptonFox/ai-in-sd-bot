# План 09. Повседневный помощник и настраиваемый лимит MCP

Статус — выполнен. Основа — [выполненный план MathMCP](08-math-mcp.md).
Прежний номер — 7.5. Следующий этап — [план 10](10-config-and-mathmcp-acceptance.md).

## 1. Роль «Повседневный помощник»

Добавить режим с ID `everyday` и командой `/everyday`. Роль помогает с
повседневными делами, погодой, напоминаниями и общими вопросами. Режимы
«Обучение», «Переводчик» и «Код-ревью» остаются доступны, по умолчанию
выбрано «Обучение».

1. Добавить описание и инструкции через существующий `PromptParts` в
   `app/modes/definitions.py`. Зарегистрировать режим в `ModeRegistry` и
   проверить его появление в `/start`, `/settings`, справке и списке команд
   Telegram. Выбор сохранять в существующем `user_settings.mode`.
2. На обычный вопрос отвечать прямо, без MCP. Прогноз и советы о зонте или
   одежде основывать на `get_weather`. Для напоминания уточнять недостающие
   данные и показывать действующую карточку подтверждения. Создание происходит
   после подтверждения владельцем, с текущей защитой от повторов.
3. Роль задаёт профиль ответа через промпт. В `everyday` модель получает тот
   же каталог инструментов и ресурсов из MCP discovery, что и в других
   пользовательских режимах. Она может вызвать MathMCP, прочитать расписание
   или использовать другой доступный инструмент по запросу пользователя.
   Для развёрнутого учебного разбора можно предложить `/study`; переключение
   добровольное. К вызовам применяются общие проверки аргументов, бюджета
   и подтверждения действий.
4. Использовать существующие цикл агента, контекст, очередь и подтверждения.
   В промпте описать типичные для роли сценарии и выбирать инструмент по запросу.
   Фоновая доставка напоминаний и маршрутизация специалистов входят в Lab 3.

## 2. Лимит вызовов MCP

Переиспользовать существующую переменную `AGENT_MAX_TOOL_CALLS` и задать
значение по умолчанию **5**. Сейчас переменная уже читается из окружения,
но `Settings` принимает только 1–2, а PostgreSQL ограничивает оба счётчика
значением 2.

1. Задать единый дефолт 5 для настроек и сервиса. Принимать положительное
   целое, помещающееся в PostgreSQL `INTEGER`. Явное значение в окружении
   или `.env` имеет приоритет над дефолтом. В `.env.example` поставить
   `AGENT_MAX_TOOL_CALLS=5`. Для текущих инсталляций с явным `=2` переход
   на новый лимит выполняется заменой строки и перезапуском бота.
2. Добавить новую миграцию для `agent_events.calls_used` и
   `pending_confirmations.calls_remaining`. Заменить проверки диапазона
   0–2 на проверки неотрицательности. Убрать SQL-дефолт 2 для
   `calls_remaining`, поскольку при создании подтверждения репозиторий
   передаёт остаток явно. Уже применённые миграции и существующие значения
   сохранить.
3. Учитывать каждый фактический вызов инструмента и чтение ресурса в общем
   бюджете исходного события. Подтверждённая мутация и её допустимые повторы
   расходуют сохранённый остаток. Подготовка карточки, discovery и локальное
   уточнение его не расходуют. При попытке выйти за лимит возвращать
   `call_budget` до следующего RPC. Сохранённый остаток старой карточки
   не пересчитывать после изменения конфигурации.
4. Передавать эффективный лимит из `Settings` в рабочее приложение и
   скрипт оценки маршрутизации, чтобы число в отчёте совпадало с фактическим
   ограничением. `AGENT_MAX_LLM_STEPS`, тайм-ауты и лимит PNG действуют
   независимо. Обновить описание лимита в README и `spec.md`.

## 3. Приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Выбор роли | Кнопка и `/everyday` доступны, выбранная роль сохраняется и восстанавливается |
| Общий вопрос, прогноз, напоминание | Обычный ответ без MCP, погода по данным инструмента, создание только после подтверждения |
| Доступ к MCP | `/everyday` получает общий каталог и выполняет, например, `math_plot` и чтение расписания. Неизвестный инструмент отклоняется общей проверкой во всех режимах |
| Настройки | Без переменной лимит 5, явные 2 или 6 применяются, ноль и нецелое значение дают ошибку конфигурации |
| Лимит в PostgreSQL | Пять смешанных чтений между серверами и ресурсами проходят, шестое блокируется. Повтор события не обнуляет бюджет |
| Подтверждение и миграция | После четырёх чтений возможен один подтверждённый вызов. Старые события и карточки сохраняют счётчики после миграции |

Прогнать locked pytest, ty и Ruff. Проверки миграции и счётчиков выполнить
на PostgreSQL в Docker с `RUN_INTEGRATION=1`. Тесты роли используют подставные
LLM, MCP и Telegram. Реальные запросы и выкладка проходят отдельно при
явной авторизации.

## Результат

- `/everyday` доступен в Telegram и сохраняется в настройках пользователя.
  Роль использует общий каталог MCP, включая графики и расписание.
- `AGENT_MAX_TOOL_CALLS` по умолчанию равен 5. Миграция `0005_agent_call_budget.sql`
  сохраняет прежние счётчики. Тесты проверяют пять вызовов, отказ на шестом,
  повтор события и подтверждение после четырёх чтений.
- Прошли 659 обычных и 19 интеграционных проверок, включая миграцию базы с
  сохранёнными счётчиками. Также прошли ty, Ruff и проверка lock-файла.
- Выпуск установлен на `de.krfx.ru` через SSH и Compose. Проверены регистрация
  команд Telegram, миграция, эффективный лимит 5 и discovery обоих MCP.
  PostgreSQL продолжил работу в прежнем контейнере. Бот, БД и оба MCP прошли
  проверки готовности.
