# Актуальный план lab2: Telegram-агент с двумя транспортами MCP

Дата: 2026-10-19. Статус: план подготовлен, реализация не начата.

Подготовительный этап: [переход на uv и обновление Docker](03-uv-migration.md).
Требования: [методичка, lab2](../../labs-guide.md#lab2).

## 1. Изменения относительно первоначального плана

- Сохраняются два транспорта по инициативе автора: stdio и Streamable HTTP.
  Для сетевого транспорта вместо первоначального SSE выбран Streamable HTTP.
- Зависимости, Docker и CI переводятся на uv по отдельному плану.
- Существующая структура приложения развивается без глобального переписывания.
- Спецификация готовится до реализации. Тесты и общая проверка собраны в отдельный
  этап; во время разработки достаточно коротких проверок затронутого сценария.
- Миграции начинаются с `0003`, поскольку `0002_dialog_summaries.sql` уже существует.
- Явно добавлены полный tool-calling цикл, защита от повторной подготовки действия,
  восстановление после потери ответа и проверка результатов инструментов.
- Все содержательные планы и их история находятся в `docs/plans`.

## 2. Границы компонентов

```text
app/
  handlers/                 # существующие обработчики + confirmations.py
  services/
    dialog_service.py       # фасад: режимы, контекст, история
    agent_service.py        # цикл LLM → инструмент → LLM
    confirmation_service.py # подготовка, подтверждение, отмена, повторы
  core/
    schemas/                # существующие DTO + agent.py и tools.py
    clock.py                # подменяемое текущее время
  llm/                      # существующий клиент с полной поддержкой tools
  mcp/
    client.py               # discovery, call_tool, read_resource
    transports.py           # открытие stdio / Streamable HTTP
    policy.py               # разрешённые действия, правила подтверждения
  mcp_server/
    __main__.py             # CLI и выбор транспорта
    config.py               # настройки сервера без обязательного BOT_TOKEN
    server.py               # регистрация инструментов и ресурса
    weather.py
    schedule.py
    reminders.py
  db/                       # существующие миграции и репозитории + новые
  data/schedule.json
```

`DialogService` сохраняет команды и режимы lab1, вызывает `AgentService` через
композицию. Агент и сервис подтверждений не импортируют Telegram-типы. Результат
обработки содержит текст, тип решения и необязательный идентификатор подтверждения;
кнопки создаёт обработчик. SQL остаётся в репозиториях.

Единый `UserQueueManager` сохраняется. Явно закрепить место захвата блокировки для
каждого входного сценария и исключить повторный захват внутри вложенного сервиса.
Защита от конкурентных мутаций обеспечивается также БД, а не только очередью процесса.

## 3. Зафиксированные решения

### Транспорты и жизненный цикл

- `stdio`: локальный дочерний MCP-процесс, Inspector и интеграционные проверки.
- `streamable-http`: отдельный `mcp-server` в Compose, URL
  `http://mcp-server:8000/mcp`; порт по умолчанию не публикуется наружу.
- Одна реализация инструментов для обоих транспортов, один Dockerfile и общий образ.
- Конфигурация: `MCP_TRANSPORT`, `MCP_SERVER_URL`, `MCP_TIMEOUT`,
  `AGENT_MAX_TOOL_CALLS=2`, отдельный предел шагов LLM, путь расписания.
- Выбрать и закрепить совместимую версию SDK и используемый API; не оставлять
  неограниченное `mcp>=1.3.0` при реализации под конкретную основную версию.
- Подключение, discovery и закрытие MCP/HTTP-клиентов организовать в жизненном
  цикле приложения. Для stdio stdout отвести протоколу, логи направлять в stderr.
- При недоступности MCP бот отвечает на обычные вопросы; запросы актуальных
  данных получают объяснение недоступности. Предусмотреть ограниченное переподключение.
  Готовность MCP отражать отдельно, не блокируя запуск обычного диалога.

### Контракты инструментов

| Примитив | Вход | Результат и ограничения |
|---|---|---|
| `get_weather` | `city`, 1–100 символов после trim | Город/страна, температура °C, условия, ветер с единицами, время наблюдения и зона; при неоднозначности — различимые варианты |
| `get_schedule` | `date`, строго `YYYY-MM-DD` | Занятия `start`, `end`, `title`, `location`; пустой список допустим |
| `add_reminder` | `text`, 1–500 символов; `remind_at`, ISO 8601 с явной зоной | ID, нормализованное время, зона, признак создания; только будущее время и подтверждённое действие |
| `schedule://current-week` | Настроенная IANA-зона и часы сервера | Понедельник–воскресенье, занятия сгруппированы по датам; только чтение |

Для инструментов задать `inputSchema`, `outputSchema`, `structuredContent`;
неизвестные и лишние аргументы отклонять. Клиент проверяет вход и выход, сервер
повторно валидирует вход. Схемы получает discovery; Telegram-хэндлеры их не дублируют.
Для недели зафиксировать серверную IANA-зону в конфигурации; личную зону напоминаний
хранить в настройках пользователя. Расписание — обезличенные данные минимум на 2–3 недели.

Погода использует Open-Meteo с конечными таймаутами и ограниченными повторами чтения.
При совпадающих названиях городов нельзя выбирать первый результат: вернуть варианты
со страной/регионом и запросить уточнение. Путь расписания задаёт только конфигурация.

### LLM и история

- Расширить `LLMRequest` описаниями tools; корректно сериализовать assistant tool calls
  и tool results с `tool_call_id`.
- Разбирать JSON-строку аргументов, валидировать структуру, обрабатывать повреждённый JSON.
- Ответ только с `tool_calls` и без текста считать допустимым; не подменять
  пользовательский ответ скрытым reasoning модели.
- Структурированно различать `respond`, `clarify`, предложение вызова инструмента.
  Для native tool calling определить проверяемый контракт различения текстового
  ответа и уточнения; не классифицировать их регулярными выражениями по ответу.
- Не более двух фактических MCP-вызовов на исходное сообщение, включая отложенное
  действие после подтверждения. Считать каждый вызов в пакете отдельно; discovery
  при запуске не включать в пользовательский бюджет. Отдельно ограничить шаги LLM.
- Промежуточный протокол хранить в памяти текущего запуска; в историю сохранять вопрос
  и итоговый ответ, детали решения — в аудит. Это сохраняет текущую компактизацию.
- Результат инструмента — недоверенные данные. Роль `tool` дополняется проверкой
  схем, allowlist и программным контролем мутаций; сама по себе роль не даёт защиты.

### Подтверждения, идентичность и время

- В сервис передавать доверенный контекст исходного Telegram update, включая
  стабильную идентичность события. `request_id` остаётся идентификатором трассировки.
- Подготовку дедуплицировать по исходному событию и позиции действия с ограничением
  уникальности в БД; повтор не создаёт новый pending и не обновляет TTL.
- Модель формирует только `text` и `remind_at`. Владелец, ключ идемпотентности и
  контекст подтверждения поступают от приложения, отдельно от аргументов модели.
- Для HTTP аутентифицировать приложение; `_meta` и `X-User-Id` сами по себе
  не являются авторизацией. Для stdio описать доверенный запуск дочернего процесса
  и проверяемый контекст конкретного запроса. Исключить общий изменяемый current_user.
- Связать серверный вызов с сохранённым подтверждённым действием и неизменяемым
  payload; произвольный клиент без доверенного контекста получает отказ.
- Состояния: `pending → confirmed → executing → succeeded`; из `pending` возможны
  `cancelled` и `expired`. Неопределённый исход выполнения требует сверки по тому же
  ключу; окончательный отказ фиксируется как `failed`.
- Подтверждение принимать атомарно только от владельца в пределах TTL ≤ 5 минут.
  Перед новым выполнением проверять актуальность времени; отменённое или изменённое
  действие не использовать. Для изменения текста/времени требуется новое подтверждение.
- Уникальность ключа в `reminders` и транзакции защищают от конкурентных повторов.
  Потеря ответа после INSERT не должна приводить ко второй записи: повтор получает
  сохранённый результат. Описать восстановление зависшего `executing` после перезапуска,
  не удерживая транзакцию БД во время сетевого вызова. Восстановление уже принятой
  операции не выдаёт новое разрешение и не продлевает TTL подтверждения.
- Локальное время интерпретировать только по сохранённой IANA-зоне пользователя.
  Если её нет — запросить `/timezone`; неоднозначное/несуществующее время DST уточнять.
  Использовать aware datetime, `zoneinfo`, `tzdata` и подменяемые часы без обязательного freezegun.
- Доставка уведомлений в назначенное время относится к lab3 и в этот объём не входит.
