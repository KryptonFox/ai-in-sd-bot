## 1. Результат и границы

Один запрос обрабатывается как единая операция: повторная доставка не меняет
память повторно, история сохраняется согласованно с результатом, неизвестный исход
создания напоминания сверяется с БД. Обычные ответы и инструменты проходят через
один агентный цикл. Запрос «Нужен ли сегодня зонт в казани?» приводит к поиску
Казани и ответу по прогнозу осадков, а не по догадке или только текущей погоде.

- Сохраняются Python 3.12, uv, ty, Ruff, aiogram, PostgreSQL, текущий LLM endpoint,
  три режима, три MCP-инструмента, stdio и Streamable HTTP.
- Миграции добавляются после `0003`; старые миграции и данные не переписываются.
  Исторический тег `lab2` остаётся на прежнем коммите.
- Целевой режим — один процесс бота и сериализация запросов одного пользователя.
  SQL-транзакции не удерживаются во время LLM/MCP-вызовов.
- Не вводятся агентный фреймворк, multi-agent runtime, распределённые блокировки,
  event sourcing, outbox и восстановление каждого шага после перезапуска.
- Не вводятся общий морфологический движок, база всех городов, regex-маршрутизатор
  по слову «зонт» и правило «Казань всегда означает Россию».
- Python-комментарии/docstrings не добавляются. Типы явные; SDK остаются в адаптерах,
  SQL — в repositories. Секреты, пользовательский текст и reasoning не логируются.

## 2. Что установлено про погоду

| Участок | Проблема | Последствие |
| --- | --- | --- |
| Описание `get_weather` | Требует название «ровно из запроса», не объясняя нормальную форму | Конфликт с преобразованием «в Казани» → `Казань` |
| Геокодирование | Любые два валидных результата означают ambiguous | Не устраняются дубли и не выделяется единственное точное совпадение |
| Страна/регион | Qualifier отрезается, затем строго сравнивается с локализованными country/admin1 после первых десяти результатов | Английская страна/ISO-код могут быть отвергнуты, нужный результат может не попасть в выдачу |
| Погода | Запрашиваются только текущие температура, weather code и ветер | Для решения о зонте на сегодня нет прогноза осадков |
| Проверка 12/12 | Routing eval использует dry run и сравнение аргументов | Не проверяются поиск города, forecast и итоговый ответ |

Через MockTransport подтверждено: два одинаковых объекта Казани дают `ambiguous`;
`Казань, Russia` отбрасывает объект с `country=Россия`; `Казани` передаётся в `name`
без изменения. Последняя проверка доказывает передачу строки, а не отсутствие alias
у живого геокодера. Сбой текущей LLM на пользовательском запросе пока не воспроизведён.

[Geocoding API](https://open-meteo.com/en/docs/geocoding-api) документирует поиск
по имени, qualifier страны/региона и `countryCode`; преобразование русских падежей
не является его контрактом. Текущий код удаляет qualifier до обращения к API.
[Forecast API](https://open-meteo.com/en/docs) предоставляет вероятность и количество
осадков, но текущий адаптер их не запрашивает.

## 3. Расширенный B7: структура и контракты

Перенос private-методов в другие файлы сам по себе не считается выполнением B7.

| Компонент | Ответственность |
| --- | --- |
| `DialogService` | Полный запрос: сериализация, claim/replay, настройки, ContextBuilder, агент, terminal commit |
| `ContextBuilder` | Snapshot истории, роль/summary/статусы действий, бюджет и ограниченная компактизация |
| `AgentService` | Явный цикл модели и переходы continue/final/await_confirmation, состояние запуска |
| `ToolExecutionService` | Локальная политика read/confirmation, проверка обнаруженной схемы, бюджет и доменная интерпретация результата |
| `ConfirmationService` | Подготовка, владелец/TTL, подтверждение/отмена, исполнение и сверка неизвестного исхода |
| Repositories / `TurnStore` | Атомарные claim/commit-turn/commit-compaction/reset и чтение статусов |
| Handlers + форматтеры | Telegram event key, typing, кнопки, представление DTO и доставка |
| LLM/MCP adapters | SDK, транспорт, discovery, wire validation и безопасная диагностика |

- [x] Ввести строгие варианты `Acquired / Replay / InProgress` и
  `Continue / Final / AwaitConfirmation`; исключить prepare без ID подтверждения
  и технический busy-статус, выглядящий сохранённым ответом.
- [x] Явно описать состояния запроса и подтверждения. Разделить отказ до эффекта,
  прерывание, неизвестный исход мутации и окончательный результат.
- [x] Ввести узкие порты хранения/исполнения для изоляции реальных side effects,
  без интерфейса и обёртки на каждый метод.
- [x] Оставить единственный production-путь ответа через `AgentService`.
  Генерация summary остаётся отдельной задачей `ContextBuilder`.
- [x] Перенести Markdown и тексты статусов/подтверждений в форматтеры.
  Сохранить команды, кнопки и три режима.
- [x] Убрать доступ обработчиков к `agent.mcp/confirmations` и внутренним locks;
  очередь принадлежит service entrypoint и захватывается один раз.
- [x] Убрать duck typing для объявленных портов. `get_context_length` вызывать
  как async-контракт; передавать время и настройки явно.
- [x] Интерпретировать погоду только для `get_weather`, а не любого payload
  со `status`. Доменная tool policy остаётся небольшой; SDK в неё не переносится.

## 4. B1–B2: память и единая обработка запроса

- [x] Выполнять claim/replay до компактизации и других вызовов модели.
  Локальным обращениям без внешнего event key выдавать UUID вместо `local:None`.
- [x] Атомарно сохранять результат и обе реплики, с уникальностью по событию.
  Миграция сохраняет читаемость старой истории без event key.
- [x] Replay не вызывает LLM, компактизацию и новые записи. `InProgress`
  показывается пользователю, но не добавляется в память.
- [x] Атомарно сохранять summary и удалять только вошедшие в неё сообщения.
  Убрать подавление storage-ошибок в методах истории/summary.
- [x] Атомарно удалять сообщения и summary при reset. Все изменения диалога
  сериализуются на service entrypoint. При этой гарантии одного процесса
  отдельная универсальная система ревизий истории не вводится.
- [x] Генерировать summary вне SQL-транзакции, сохраняя сериализацию пользователя;
  выбирать целые пары реплик, не случайную половину диалога.
- [x] Добавлять в следующий контекст проверенный статус действия из confirmation
  store. Успех/отмена/recovery не должны зависеть от старого вопроса о подтверждении.
- [x] Разделить продуктовый аудит и диагностические метрики: обязательные записи
  согласовать с commit операции; вспомогательная telemetry не меняет её исход.
  Ошибка записи аудита не подменяет исходную LLM-ошибку.

Внутренняя идемпотентность не обещает exactly-once доставку Telegram. Отдельный
механизм гарантированной отправки ответа в этот план не входит.

## 5. B3: подтверждение и неизвестный результат

- [x] Разделить доказанный отказ и неизвестный исход после dispatch.
  `invalid_output` после мутации не означает отсутствие записи.
- [x] Неизвестный исход сверять по существующему idempotency key через действующий
  recovery; не предлагать пользователю повторное создание до сверки.
- [x] Сохранить owner, TTL, сравнение подтверждённых аргументов, лимит попыток
  и серверную идемпотентность. Не сбрасывать расход при retry/callback.
- [x] Отразить результат в источнике статуса для контекста. Автоматические
  Telegram-уведомления после recovery не добавляются.
- [x] Сохранить текущую политику: одно pending-напоминание; reset/смена режима
  не отменяют сохранённое подтверждение; timezone действия не меняется задним
  числом. При необходимости пояснить это в существующей справке.

## 6. B4–B5: отмена, dry run, завершение и простой retry

- [x] Исправить cleanup очереди при отмене до и после acquire. Освобождать lock
  только если он захвачен; не оставлять фиктивный busy.
- [x] Общая граница запуска обрабатывает отмену, deadline и ошибки хранения.
  После кооперативного прерывания запрос не висит десять минут в processing;
  `CancelledError` после cleanup повторно выбрасывается.
- [x] При запуске одного процесса завершать оставшиеся незаконченные запросы
  предыдущего процесса как interrupted. Подтверждения продолжают свой recovery;
  их неизвестный исход не превращается в обычный interrupted turn.
- [x] Принять простой retry: после успешного чтения и несформированного ответа
  старый запуск не имитирует продолжение без данных. Пользователь может отправить
  новый запрос с новым event key. До внешнего действия допустим безопасный повтор
  в исходном бюджете; неизвестная мутация всегда проходит сверку B3.
  Привести кнопку retry к этой семантике, не сбрасывая бюджет старого события.
- [x] `dry_run` запрещает все записи, включая audit/finish/fail и error path.
  Он может вызывать модель, но не исполняет MCP-tools и не готовит confirmation.
- [x] Проверять finish reason до tool dispatch: length с текстом явно обозначается
  как обрезанный ответ; tool calls незавершённой генерации не выполняются.
  Автоматическое бесконечное продолжение не вводится.

## 7. B6: простой общий бюджет

- [x] Учитывать инструкции, summary, историю, текущий запрос, схемы и результаты
  tools, резерв вывода. Настроенный предел памяти — верхнее ограничение.
- [x] Начать с консервативной оценки с запасом, без обещания точности токенизатора
  любого провайдера. Проверять бюджет перед каждым LLM step.
- [x] Ограничить вход/выход summary и размер tool output без разрушения JSON;
  не отправлять всю накопленную историю одним запросом компактизации.
- [x] Слишком длинный текущий запрос не обрезать молча: вернуть понятный ответ.
  Сохранить границы доверия summary и результатов tools.
- [x] Ввести общий deadline, включающий context build и компактизацию, отдельно
  от timeout одного вызова. Сохранить предел двух MCP-вызовов и числа шагов модели;
  новые настройки валидировать и описать.

## 8. Погода: смысл запроса, место и прогноз

- [x] Добавить короткие примеры «в Казани» → `Казань`, «в Нижнем Новгороде» →

- [x] Использовать город из истории только если пользователь явно его назвал.

- [x] Выделить разрешение места из прогноза. Передавать явный qualifier провайдеру
  до ограничения выдачи; countryCode использовать только для указанной страны.
- [x] Нормализовать сравнение, устранить дубли одного географического объекта,
  выделить единственное точное совпадение перед неточными. Разные реальные
  одноимённые города требуют уточнения. Не выбирать первый/самый населённый
  вариант только по позиции или известности.
- [x] Возвращать различимые страну/регион. Разделять неизвестный город,
  неоднозначное место и недоступность сервиса.
- [x] Сохранить вход `get_weather(city)`, расширить проверяемый выход: текущие
  условия и компактный прогноз осадков на сегодня с датой, вероятностью,
  количеством и единицами. Получать их одним forecast-запросом, без нового tool.
- [x] Определять сегодня по timezone найденного города. Различать текущие условия
  и прогноз за день; дневной максимум вероятности не выдавать за вероятность

- [x] При отсутствии прогноза не делать уверенный вывод о зонте. Для дат вне

   повторять её реализацию в основном рефакторинге не требуется.
6. Один завершающий общий прогон после целевых проверок во время разработки.

модели mock-тест не объявляется доказательством качества её распознавания запросов.
