# Спецификация lab2

Контракт реализации lab2. Базовая приёмка — [план 04](docs/plans/lab2/04-lab2-implementation.md); текущие изменения — [план 06](docs/plans/lab2/06-agent-reliability-and-weather.md).

## Назначение и пользовательские сценарии

Бот продолжает приложение лабораторной работы № 1 и через MCP предоставляет актуальные данные и подготовку напоминаний. Пользователь может:

- задать обычный вопрос и получить ответ без вызова инструмента;
- запросить погоду в городе; при неоднозначном городе получить варианты и уточнить запрос;
- узнать расписание на дату или прочитать ресурс текущей недели;
- подготовить напоминание, проверить показанные текст и время, подтвердить либо отменить его;
- задать IANA-часовой пояс командой `/timezone`, просмотреть доступные возможности через `/tools` и получить краткое объяснение последнего решения через `/why`.

Недоступность MCP не мешает обычному диалогу. Для недоступных актуальных данных бот сообщает об ошибке и не утверждает, что действие выполнено. Доставка напоминаний по расписанию относится к lab3.

## MCP-контракт

Сервер публикует три инструмента и ресурс `schedule://current-week`:

- `get_weather(city)` возвращает город и страну, температуру в °C, погодные условия, ветер с единицами, время наблюдения и зону. Выход также содержит `today`: дату, дневную вероятность осадков (%), количество (мм) и `period=whole_day` в timezone города, либо null при отсутствии прогноза. Дубли одного места устраняются, единственное точное совпадение выбирается перед похожими; разные одноимённые места требуют уточнения. Склонённое название модель приводит к нормальной форме, qualifier передаётся геокодеру до ограничения выдачи.
- `get_schedule(date)` принимает строгую дату `YYYY-MM-DD` и возвращает занятия с началом, концом, названием и местом; пустой список допустим.
- `add_reminder(text, remind_at)` принимает текст длиной 1–500 символов и ISO 8601 время с явной зоной. Результат содержит идентификатор, нормализованное время, зону и признак создания. Создание возможно только для будущего времени и подтверждённого действия.
- `schedule://current-week` доступен только для чтения и содержит неделю с понедельника по воскресенье в настроенной серверной IANA-зоне.

Входные и выходные схемы инструментов обнаруживаются через MCP discovery. Клиент и сервер валидируют данные; схемы строгие, лишние поля запрещены (`additionalProperties: false` / эквивалент `extra=forbid`). `outputSchema` принимает union успешного результата и типизированной ошибки. Результаты возвращаются в `structuredContent`; они считаются недоверенными данными. Обработчики Telegram не содержат копий MCP-схем.

Агент использует нативный tool calling OpenAI SDK. Решение маршрутизации типизировано как `respond`, `clarify` или предложение вызова инструмента. `respond` и `clarify` представлены виртуальным решением приложения (`finish_response`), а не MCP-инструментом; обычный текстовый ответ без `tool_calls` принимается как совместимый fallback с lab1. Приложение проверяет разрешённое имя, аргументы, результат и права перед дальнейшим шагом. OpenAI SDK используется только для LLM-клиента; MCP SDK используется только для MCP-клиента/сервера.

На исходное сообщение допускается не более двух фактических вызовов MCP, включая вызов после подтверждения. Каждый вызов в пакете учитывается отдельно; discovery при старте не расходует пользовательский лимит. Цикл ограничен четырьмя шагами LLM.

Поддерживаются `stdio` для локального процесса и Streamable HTTP для внутреннего сервиса. По HTTP приложение аутентифицируется Bearer-токеном `MCP_SHARED_SECRET`; общий ключ имеет длину не менее 32 символов. Сервер связывает подтверждение с сохранённым в БД действием, владельцем и неизменяемой нагрузкой. Самостоятельные `X-User-Id` или `_meta` не удостоверяют пользователя. Для stdio доверенный контекст передаётся конкретному запросу и проверяется сервером.

## Подтверждения, повторная доставка и время

Предложение напоминания содержит только текст и время. Владельца, идентичность исходного события и ключ идемпотентности задаёт приложение. Подготовка уникальна по исходному событию и позиции действия в БД; повторная доставка не создаёт новую запись ожидания и не продлевает TTL. Payload после подготовки неизменяем.

Состояния действия: `pending → confirmed → executing → succeeded`; из `pending` также возможны `cancelled` и `expired`, а окончательный отказ фиксируется как `failed`. Только владелец может атомарно подтвердить действие в течение настроенного TTL, не превышающего 300 секунд (по умолчанию 300). Повторное или конкурентное подтверждение не создаёт дубль. Изменение текста или времени требует новой подготовки и нового подтверждения.

Выполнение связывается с подтверждённым payload и идемпотентным ключом, уникальным в хранилище напоминаний. После потери ответа повтор возвращает сохранённый результат. Зависший `executing` сверяется и восстанавливается после перезапуска с тем же ключом; восстановление не создаёт новое разрешение, не меняет payload и не продлевает TTL подтверждения. Сетевой вызов не удерживает транзакцию БД.

Полный запрос координирует DialogService: проверка повтора предшествует контексту, а итог, обе реплики и продуктовый аудит сохраняются одной транзакцией. Компактизация и reset атомарны; очередь пользователя принадлежит service entrypoint. Старые локальные вызовы без внешнего event key получают уникальный UUID.

Общий deadline после входа в очередь — AGENT_TIMEOUT (240 с), резерв вывода — LLM_MAX_TOKENS (1024). Контекст оценивается консервативно вместе со схемами и результатами tools. Dry run может вызывать LLM, но не пишет БД и не исполняет MCP. Незавершённые tool calls при finish_reason=length не выполняются. После частичного чтения прерванный запуск требует нового запроса; восстановление промежуточных шагов и exactly-once доставка Telegram не обещаются. При старте одного процесса незавершённые processing становятся interrupted; подтверждения восстанавливаются отдельно, включая invalid_output после возможной мутации.

Локальное время разбирается только по сохранённой IANA-зоне пользователя. Если зона неизвестна, бот просит задать её через `/timezone`; неоднозначное или несуществующее местное время при переходе DST требует уточнения. Используются timezone-aware даты и подменяемые часы. Значения по умолчанию: транспорт `stdio`, тайм-аут MCP 10 секунд, не более 2 вызовов MCP и 4 шагов LLM, TTL подтверждения 300 секунд, серверная зона расписания `Europe/Moscow`.

## Границы и эксплуатационные требования

Обработчики Telegram отвечают за представление, services оркестрируют сценарии, SQL принадлежит repositories. Типы OpenAI SDK ограничены слоем `llm`, MCP SDK — MCP-слоем. В журнал аудита входят время, request ID, решение, безопасное резюме параметров, результат валидации и выполнения, длительность и краткая причина; пользовательский текст, секреты, Telegram ID и chain-of-thought не попадают в текстовые журналы. В БД хранится безопасная ограниченная сводка аргументов для аудита и `/why`.

Автоматические unit-тесты используют моки для внешних API, LLM и транспорта. Интеграционные проверки используют настоящий PostgreSQL в Docker только при `RUN_INTEGRATION=1`. Сценарии ошибок должны проверять валидацию, недоступность сервиса, дубли событий, повторное подтверждение, потерю ответа и восстановление выполнения. Реальные сети и отправка сообщений выполняются только по явной авторизации.
