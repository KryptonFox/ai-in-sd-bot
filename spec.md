# Спецификация lab2

Контракт реализации lab2. Базовая приёмка — [план 04](docs/plans/lab2/04-lab2-implementation.md); изменения надёжности — [план 06](docs/plans/lab2/06-agent-reliability-and-weather.md); упрощение MCP и контекста — [план 07](docs/plans/lab2/07-post-lab2-simplification.md).

## Назначение и пользовательские сценарии

Бот продолжает приложение лабораторной работы № 1 и через MCP предоставляет актуальные данные и подготовку напоминаний. Пользователь может:

- задать обычный вопрос и получить ответ без вызова инструмента;
- запросить погоду в городе; при неоднозначном городе получить варианты и уточнить запрос;
- узнать расписание на день или неделю, в том числе прочитать ресурс текущей недели;
- подготовить напоминание, проверить показанные текст и время, подтвердить либо отменить его;
- задать IANA-часовой пояс командой `/timezone`, просмотреть доступные возможности через `/tools` и получить краткое объяснение последнего решения через `/why`.

Недоступность MCP не мешает обычному диалогу. Для недоступных актуальных данных бот сообщает об ошибке и не утверждает, что действие выполнено. Доставка напоминаний по расписанию относится к lab3.

## MCP-контракт

Отдельный FastMCP 4.1.5 сервер `student-tools` находится в `mcp_servers/student_tools` и публикует четыре инструмента и ресурс `schedule://current-week`:

- `get_weather(city?, date?)` без города использует Санкт-Петербург, без даты — сегодня в зоне города. Возвращает текущие условия, город и страну, температуру в °C, ветер с единицами, время наблюдения и зону. `today` содержит дневной прогноз осадков (% и мм); `forecast` — прогноз на `requested_date`, включая диапазон температуры и максимальный ветер, в пределах 16 дней. Отсутствующий прогноз не подменяется текущими условиями. Склонённое название модель приводит к нормальной форме; явные страна/регион передаются геокодеру до ограничения выдачи. Дубли устраняются, точные совпадения предпочтительнее похожих. Среди точных совпадений город от 100 000 жителей выбирается автоматически, если остальные меньше 100 000 и ближайший по населению уступает минимум в 20 раз. Остальные неоднозначные места требуют уточнения. Это осознанное расширение поведения относительно строгого требования методички уточнять любое одноимённое место.
- `get_schedule(date?)` принимает строгую календарную дату `YYYY-MM-DD`, по умолчанию сегодня в `SCHEDULE_TIMEZONE`, и возвращает занятия с началом, концом, названием и местом. `data_available` отличает отсутствие данных от свободного дня (`is_free_day`).
- `get_schedule_week(date?, week_offset=0)` возвращает неделю, содержащую дату, либо неделю относительно текущей: 0 — эта, 1 — следующая. Дата и ненулевое смещение одновременно запрещены. Это дополнительный инструмент сверх базовых трёх инструментов lab2.
- `add_reminder(text, remind_at)` принимает текст длиной 1–500 символов и ISO 8601 время с явной зоной. Результат содержит идентификатор, нормализованное время, зону и признак создания. Создание возможно только для будущего времени и подтверждённого действия.
- `schedule://current-week` доступен только для чтения и содержит неделю с понедельника по воскресенье в настроенной серверной IANA-зоне.

Схемы инструментов обнаруживаются через MCP discovery. FastMCP Client компилирует входные и выходные JSON Schema-валидаторы при загрузке каталога; вход проверяется с `FormatChecker`, а успешный JSON-результат — по выходной схеме и на отсутствие NaN/Infinity. Серверные ошибки инструмента передаются как безопасная JSON-ошибка и преобразуются в `ToolFailure`; её внутреннее сообщение не раскрывается пользователю. Результаты и содержимое ресурсов считаются недоверенными данными. Обработчики Telegram не содержат копий MCP-схем.

Дневные и недельные аргументы используют общий тип `ISODate`: проверяются формат и существование календарной даты. В репозитории хранится вымышленное расписание на 2–29 сентября 2030 года. Личное расписание подключается через `SCHEDULE_PATH`; локальная копия в `.local/` игнорируется Git и не включается в Docker-образ. При развёртывании только удалённый `.env.cloud` подменяет путь с сегментом `.local` на комплектное расписание; локальная настройка остаётся неизменной. Остальные пользовательские пути сохраняются. Compose монтирует выбранный файл в MCP-сервер только для чтения.

Агент использует нативный tool calling через LLM-адаптер. Обычный текст завершает ответ; для уточнения модель вызывает локальный инструмент приложения `clarification(question)`, который не отправляется в MCP. После чтения `ToolExecutionService` возвращает `StepAction.CONTINUE`, и цикл запрашивает следующий ответ модели. MCP-клиент проверяет discovery-схемы и аннотацию `readOnlyHint`; бизнес-политика разрешает изменение только для `add_reminder`, остальным изменяющим инструментам отказывает.

Обнаруженные ресурсы представлены модели локальной функцией приложения `read_resource(uri)` с динамическим enum URI из `list_resources`. `AgentService` добавляет её схему рядом со схемой `clarification(question)`; это не MCP tool: сервер не публикует ресурс в `tools/list`, а хост перехватывает вызов и выполняет протокольный `resources/read` через FastMCP Client. Общая пакетная валидация и проверка бюджета выполняются до RPC. Результат возвращается в сообщении роли `tool` с исходным `tool_call_id` и недоверенной JSON-обёрткой (`source`, `uri`, `mime_type`, `content`). Ошибка самого resource RPC передаётся как tool error content; хост не делает автоматических повторов, а модель получает обычный следующий шаг, где может уточнить запрос или ответить с имеющимися данными. Ошибки URI, аргументов и бюджета, как и ошибки нативных MCP tools, завершают обработку. Чтения ресурсов и MCP tools используют один общий лимит двух MCP-вызовов и обычный агентный цикл максимум в четыре шага LLM. В `AgentResult.resource_uris` и продуктовый аудит записываются успешно прочитанные URI.

На исходное сообщение допускается не более двух фактических вызовов MCP, включая вызов после подтверждения. Каждый вызов в пакете учитывается отдельно; discovery при старте не расходует пользовательский лимит. Цикл ограничен четырьмя шагами LLM.

Поддерживаются `stdio` для локального дочернего процесса и Streamable HTTP для внутреннего сервиса. Compose service — `student-tools-mcp`, FastMCP server name — `student-tools`; Compose URL внутри сети `http://student-tools-mcp:8000/mcp`. По HTTP приложение аутентифицируется Bearer-токеном `MCP_SHARED_SECRET`; общий ключ имеет длину не менее 32 символов. Сервер связывает подтверждение с сохранённым в БД действием, владельцем и неизменяемой нагрузкой. Самостоятельные `X-User-Id` или `_meta` не удостоверяют пользователя. Для stdio доверенный контекст передаётся конкретному запросу и проверяется сервером.

## Подтверждения, повторная доставка и время

Предложение напоминания содержит только текст и время. Владельца, идентичность исходного события и ключ идемпотентности задаёт приложение. Подготовка уникальна по исходному событию и позиции действия в БД; повторная доставка не создаёт новую запись ожидания и не продлевает TTL. Payload после подготовки неизменяем.

Когда текст, точное время и сохранённая зона известны, модель вызывает `add_reminder` для подготовки предложения. Точный относительный интервал вычисляется от переданного приложением текущего времени. Предложение, его сохранение и кнопки подтверждения формирует приложение; текстовое обещание модели не считается подготовкой действия. Фактический вызов MCP для создания остаётся за подтверждением владельца.

Если базовый запрос помещается в окно модели, сначала подбираются последние целые пары истории с минимумом 64 токена для генерации. Оставшееся место используется для ответа в пределах настроенного максимума. Резерв длинного ответа не должен полностью вытеснять помещающуюся историю. Самые старые пары исключаются только при нехватке окна; если обязательная часть запроса не оставляет 64 токенов вывода, запрос отклоняется.

Состояния действия: `pending → confirmed → executing → succeeded`; из `pending` также возможны `cancelled` и `expired`, а окончательный отказ фиксируется как `failed`. Только владелец может атомарно подтвердить действие в течение настроенного TTL, не превышающего 300 секунд (по умолчанию 300). Повторное или конкурентное подтверждение не создаёт дубль. Изменение текста или времени требует новой подготовки и нового подтверждения.

Выполнение связывается с подтверждённым payload и идемпотентным ключом, уникальным в хранилище напоминаний. После потери ответа повтор возвращает сохранённый результат. Зависший `executing` сверяется и восстанавливается после перезапуска с тем же ключом; восстановление не создаёт новое разрешение, не меняет payload и не продлевает TTL подтверждения. Сетевой вызов не удерживает транзакцию БД.

Полный запрос координирует DialogService: проверка повтора предшествует контексту, а итог, обе реплики и продуктовый аудит сохраняются одной транзакцией. Компактизация и reset атомарны; очередь пользователя принадлежит service entrypoint. Старые локальные вызовы без внешнего event key получают уникальный UUID.

DialogService получает каталог инструментов через `ToolClient`, а состояние и выполнение подтверждений — непосредственно через `ConfirmationService`. Он не зависит от `ToolExecutionService`. `AgentService` получает каталог ресурсов из `ToolExecutionService.resources`, который предоставляет их через `ToolClient`. Выбранные URI хранятся в `AgentResult.resource_uris`; при записи аудита их список помещается под зарезервированный ключ `resource_uris` в JSONB `arguments`, рядом с ограниченными полями вызова инструмента. `/why` показывает URI как ресурсы, а не как tools, используя сохранённый аудит без запроса модели.

Общий deadline после входа в очередь — AGENT_TIMEOUT (240 с), резерв вывода — LLM_MAX_TOKENS (16384, настраивается до 131072). Контекст оценивается консервативно вместе со схемами и результатами инструментов/ресурсов. Лимит в два MCP-вызова учитывает каждый tool read, каждый resource read и подтверждённое создание напоминания; resource-вызов использует один обычный шаг LLM. Незавершённые tool calls при finish_reason=length не выполняются. После частичного чтения прерванный запуск требует нового запроса; восстановление промежуточных шагов и exactly-once доставка Telegram не обещаются. При старте одного процесса незавершённые processing становятся interrupted; подтверждения восстанавливаются отдельно, включая invalid_output после возможной мутации.

Локальное время разбирается по IANA-зоне пользователя: явно сохранённая настройка имеет приоритет, при её отсутствии приложение использует `Europe/Moscow`. Команда `/timezone` показывает эффективную зону, а `/timezone <IANA-зона>` сохраняет явный выбор. Модель не угадывает зону по городу или переписке. Неоднозначное или несуществующее местное время при переходе DST требует уточнения. Используются timezone-aware даты и подменяемые часы. Значения по умолчанию: транспорт `stdio`, тайм-аут MCP 10 секунд, не более 2 вызовов MCP и 4 шагов LLM, TTL подтверждения 300 секунд, серверная зона расписания `Europe/Moscow`.

## Границы и эксплуатационные требования

Обработчики Telegram отвечают за представление, services оркестрируют сценарии, SQL принадлежит repositories. Типы OpenAI SDK ограничены слоем `llm`: `OpenAIClient` владеет SDK-вызовами, таймаутами и безопасной диагностикой, а `llm/codec.py` преобразует DTO и проверяет ответы. FastMCP SDK types используются в `app/mcp` и `mcp_servers`; `MCPClient` владеет жизненным циклом транспорта и RPC, а `ToolCatalog` — discovery definitions и скомпилированными валидаторами. Прикладные контракты ресурсов находятся в нейтральных core DTO. В журнал аудита входят время, request ID, решение, безопасное резюме параметров, использованные ресурсные URI, результат валидации и выполнения, длительность и краткая причина; пользовательский текст, секреты, Telegram ID и chain-of-thought не попадают в текстовые журналы. В БД хранится безопасная ограниченная сводка аргументов для аудита и `/why`.

Автоматические unit-тесты используют моки для внешних API, LLM и транспорта. Интеграционные проверки используют настоящий PostgreSQL в Docker только при `RUN_INTEGRATION=1`. Сценарии ошибок должны проверять валидацию, недоступность сервиса, дубли событий, повторное подтверждение, потерю ответа и восстановление выполнения. Реальные сети и отправка сообщений выполняются только по явной авторизации.

Критерии завершения и подробные этапы находятся в [плане 04](docs/plans/lab2/04-lab2-implementation.md), требования учебной работы — в [руководстве lab2](docs/labs-guide.md#lab2). Подготовка окружения описана в [плане 03](docs/plans/lab2/03-uv-migration.md), SDK и Telegram-адаптера — в [плане 05](docs/plans/lab2/05-llm-sdk-prompts-and-telegram.md). Эта спецификация задаёт целевой контракт и сама по себе не подтверждает реализацию или приёмку.
