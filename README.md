# Telegram-бот «AI-ассистент студента»

Асинхронный Telegram-бот на базе Python 3.12 и aiogram 3, интегрированный с большими языковыми моделями (LLM) через OpenAI-совместимый API и СУБД PostgreSQL для сохранения контекста диалога, выжимок истории и настроек пользователей.

---

## 1. Стек технологий и инструменты

- **Язык и среда:** Python 3.12
- **Пакетный менеджер и виртуальное окружение:** [uv](https://github.com/astral-sh/uv)
- **Telegram фреймворк:** [aiogram 3](https://docs.aiogram.dev/) (асинхронный long polling, роутеры, фильтры, inline-клавиатуры)
- **СУБД и пул соединений:** PostgreSQL 16 (в Docker Compose), асинхронный драйвер `asyncpg` с пулом подключений
- **Миграции базы данных:** собственный асинхронный runner с `pg_advisory_lock` и контрольными суммами SHA-256 (`app/db/migrations/`)
- **LLM-интеграция:** `openai.AsyncOpenAI` (Chat Completions через HTTPX2; настраиваемый OpenAI-совместимый endpoint)
- **MCP:** Python MCP SDK; локальный транспорт `stdio` и Streamable HTTP в Compose
- **Схемы и валидация данных:** `pydantic v2` (модели запросов/ответов LLM, сообщений, валидация настроек пользователей)
- **Форматирование Telegram:** `telegramify-markdown==1.4.1` (текст + entities, готовое разбиение)
- **Служебный HTTP-сервер:** `aiohttp` (эндпоинт `/health` на порту 8080 для Docker и оркестраторов)
- **Контейнеризация:** Docker, Docker Compose
- **Проверки:** `pytest`, `pytest-asyncio`, `ruff`, `ty`; управление окружением через `uv`

## 2. Принцип работы бота

### Схема обработки запроса пользователя
1. **Приём апдейта:** Пользователь отправляет сообщение в Telegram. `aiogram` направляет его в роутер диалога (`app/handlers/dialog.py`).
2. **Трассировка и UX:** Генерируется уникальный `request_id` (передаётся через `contextvars`), в чат отправляется статус набора текста (`chat_action="typing"`).
3. **Обработка запроса:**
   - `DialogService` сериализует запросы пользователя и проверяет event key до подготовки контекста. Повтор возвращает сохранённый результат без LLM и новых реплик; технический статус обработки не попадает в память.
   - `ContextBuilder` собирает RCTF-инструкции режима, summary, целые пары реплик и проверенный статус последнего подтверждения. История, summary и результаты tools остаются данными, а не новыми системными инструкциями.
   - Metadata размера окна определяется отдельно от генерации и кэшируется по модели/endpoint; для неизвестного провайдера используется `DEFAULT_CONTEXT_LENGTH`. Общий бюджет консервативно оценивает UTF-8 размер сообщений и схем, учитывая резерв вывода; это не точный токенизатор произвольной модели.
   - При компактизации выбирается ограниченная порция старых полных пар. Новая summary и удаление исходных сообщений сохраняются одной транзакцией. `COMPACTION_KEEP_RECENT=3` округляется вверх до четырёх реплик, чтобы сохранить целые пары.
   - `AgentService` выполняет единственный цикл ответа: LLM → проверка завершения → ответ, чтение инструмента или предложение подтверждения. `ToolExecutionService` проверяет локальную политику, discovery-схемы, расход и размер результата.
   - Итог события, обе реплики и продуктовый аудит сохраняются атомарно. Сетевые вызовы не удерживают SQL-транзакции. SDK-клиенты живут до остановки приложения; неявные SDK retries отключены.
4. **Рендеринг и чанкинг:**
   - Полный Markdown один раз проходит `telegramify_markdown.convert(latex_escape=False)` с изолированной конфигурацией без emoji у заголовков/ссылок и с маркером списка `-`. Затем `split_entities(..., max_utf16_len=4096)` делит текст и entities; отправка через aiogram всегда использует `parse_mode=None`.
   - Обёртка проверяет UTF-16 offsets, допускает bold/italic/code/pre/text_link и ссылки HTTP(S). Неизвестные entities удаляются с сохранением видимого текста. Собственных парсера, HTML-рендера и splitter нет.
   - При сбое конвертации отправляется исходный текст без entities; при отказе Telegram из-за entities — видимый текст только отклонённой части. Оба plain-text пути также используют `split_entities`; сетевые и остальные API-ошибки не повторяются. Reply-to ставится на первый фрагмент, inline-кнопки — на последний. Пустой результат не отправляется.

### Режимы работы (роли)
- `/study` — **«Обучение»:** ментор студента ИТМО по математике, алгоритмам и ПО. Обосновывает решение, учитывает уровень и нужный язык; код приводит по задаче, по просьбе о подсказке не раскрывает полное решение.
- `/translate` — **«Переводчик»:** математический и технический перевод текстов, документации и кода с сохранением синтаксиса и терминологии.
- `/review` — **«Код-ревью»:** ревью кода с few-shot примерами. Анализирует найденные проблемы, оценивает алгоритмическую сложность (Big O) и предлагает улучшенный вариант реализации.

### Команды бота
- `/start` — приветственное сообщение и интерактивный выбор роли через inline-кнопки.
- `/help` — список доступных ролей и команд бота.
- `/study`, `/translate`, `/review` — быстрое переключение активной роли.
- `/settings` — интерактивный выбор температуры генерации (`0.0`, `0.3`, `0.7`, `1.0`) через inline-кнопки.
- `/reset` — атомарная очистка сообщений и summary. Сохранённые подтверждения остаются действующими; их payload и timezone не меняются задним числом.

### Описание бота

При каждом запуске бот через aiogram обновляет описание в пустом чате и краткое
описание профиля. Тексты находятся в `BOT_DESCRIPTION` и `BOT_SHORT_DESCRIPTION`
в `app/telegram.py`; они задаются для языка по умолчанию. Изменения через
BotFather `/setdescription` и `/setabouttext` для этого языка будут перезаписаны
при следующем запуске. Ошибка обновления описания записывается в лог и не мешает
боту запуститься.

### Отказоустойчивость
- **Таймауты LLM:** при превышении времени ожидания (`LLM_TIMEOUT`, по умолчанию 180 с) бот отправляет сообщение об ошибке с inline-кнопкой «🔄 Повторить».
- **Причины ошибок LLM:** бот различает ошибки ключа и прав доступа, адреса или модели, квоты, соединения, параметров запроса, формата ответа и лимита генерации. `/why` показывает понятное объяснение вместо `llm_error`. Логи `llm_start`, `llm_usage` и `llm_complete` содержат имя модели; `llm_failed` и `llm_error` — код причины, HTTP-статус и безопасную диагностику. Для ошибок формата сохраняются этап (`request_payload`, `response_decode`, `stream_decode`, `response_validation`, `tool_arguments`), тип исключения, место ошибки в коде, путь поля и причина проверки либо строка/столбец некорректного JSON. Ошибка провайдера внутри SSE сохраняет известный код и распознанную причину и не выдаётся за ошибку формата. Тексты запросов, ответы провайдера и содержимое исключений в диагностические логи не попадают.
- **Маскирование секретов:** фильтр `SecretFilter` автоматически скрывает токен бота, ключ LLM, пароли БД и параметры прокси из логов и трейсбеков.
- **Healthcheck:** HTTP-эндпоинт отдаёт `200 OK` только при одновременной доступности Telegram polling и успешном выполнении `SELECT 1` в PostgreSQL.

## 5. Запуск проекта

### Вариант 1: Запуск через `uv` (рекомендуемый)

1. **Установите `uv`** (если ещё не установлен):
   ```bash
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

2. **Подготовьте окружение:**
   ```bash
   uv sync --locked
   ```
   Python 3.12 выбирается из `.python-version`; при необходимости uv загрузит его.

3. **Запустите PostgreSQL в Docker:**
   ```bash
   docker compose -f compose.yaml -f compose.local.yaml up -d db
   ```

4. **Запустите бота:**
   ```bash
   uv run --locked python -m app
   ```

`uv` создаёт `.venv` и устанавливает зависимости по `uv.lock`. Миграции PostgreSQL
применяет само приложение при запуске перед началом long polling.

Зависимости объявлены в `pyproject.toml`, точные версии зафиксированы в `uv.lock`.
Добавление пакетов: `uv add <package>`, инструментов разработки: `uv add --dev <package>`.
После изменения зависимостей коммитьте оба файла. В CI и Docker используется
`--locked`: несоответствие конфигурации lock-файлу приводит к ошибке.

---

### Вариант 2: Запуск через скрипты автоматизации

**Linux / macOS:**
```bash
bash scripts/start.sh
```

**Windows (PowerShell):**
```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

Для обёрток нужны uv в `PATH` и Docker Compose. Скрипт подготавливает окружение
через `uv sync --locked`, запускает PostgreSQL и бота. Системная установка Python
для обёрток не требуется: интерпретатором управляет uv. Запуск возможен из любого каталога.

---

### Вариант 3: Только подготовка окружения для IDE

Если вы хотите запускать и отлаживать бота напрямую из VS Code или PyCharm:
```bash
bash scripts/start.sh --setup-only
```
После этого выберите интерпретатор `.venv/bin/python` (или `.venv\Scripts\python.exe` на Windows) и запускайте модуль `app`.

## 8. Деплой в Yandex Cloud

Docker-образ собирается на Python 3.12 с uv 0.13.1. Runtime-зависимости устанавливаются
из `uv.lock` при сборке без группы `dev`; контейнер запускается от `student` и использует
`/app/.venv/bin/python` для приложения и healthcheck. При старте пакеты не скачиваются.
Для локальной проверки образа: `docker build -t ai-in-sd-bot:uv .`.
Архив развёртывания включает конфигурацию uv, исходники, SQL-миграции и JSON из
`app/data`, исключая `.env`, локальные окружения и ключи.

Скрипты `scripts/deploy.sh` (Linux/macOS) и `scripts/deploy.ps1` (Windows) автоматизируют развёртывание бота на виртуальной машине в Yandex Cloud:

# Остановка и запуск виртуальной машины

## Lab 2: MCP-агент

Lab2 расширяет этого бота четырьмя MCP-инструментами и ресурсом текущей недели:
`get_weather`, `get_schedule`, `get_schedule_week`, `add_reminder` и
`schedule://current-week`. Клиент
получает их входные и выходные схемы через discovery, проверяет аргументы и
структуру результатов. Погода запрашивается у Open-Meteo, расписание загружается
из JSON-файла, напоминания и подтверждения хранятся в PostgreSQL.

Локально по умолчанию используется `stdio`: бот запускает MCP-сервер как дочерний
процесс, поэтому отдельный порт и отдельная команда запуска сервера не нужны.
Сервер получает отдельное окружение без Telegram- и LLM-секретов. Для HTTP
используется Streamable HTTP; бот подключается к `/mcp/` с `Authorization: Bearer`.
Сервер слушает внутреннюю сеть Compose и не публикует порт наружу. Для этого
режима задайте один и тот же `MCP_SHARED_SECRET` длиной не менее 32 символов в
окружении бота и сервера. В режиме `stdio`, если секрет не задан, клиент создаёт
временный секрет для запуска дочернего процесса.

Для локального запуска MCP-сервера отдельно (например, для MCP Inspector)
подготовьте `.env` с PostgreSQL-параметрами и `MCP_SHARED_SECRET` длиной не менее
32 символов. Не вставляйте реальный секрет в документацию, скриншоты или отчёт.
Затем запускайте один из транспортов:

```bash
uv run --locked python -m app.mcp_server --transport stdio
uv run --locked python -m app.mcp_server --transport streamable-http
```

Для Inspector 2.12 настройте stdio-сервер командой `uv` и аргументами
`run --locked python -m app.mcp_server --transport stdio`, передав PostgreSQL-
переменные и общий `MCP_SHARED_SECRET` в окружение процесса. Для Streamable HTTP
укажите URL `http://127.0.0.1:8000/mcp/` и заголовок
`Authorization: Bearer <MCP_SHARED_SECRET>`; секрет должен совпадать с серверным.
Используйте отдельную тестовую базу и тестовую учётную запись, особенно при
проверке изменения данных.

В облачном сценарии скрипт развёртывания сам создаёт и сохраняет ключ MCP;
при ручном запуске Compose задайте общий `MCP_SHARED_SECRET` в локальном `.env`.
После этого выполните:

```bash
docker compose --profile cloud up --build -d
```

Команда `/tools` показывает только обнаруженные возможности и помечает чтение и
изменение. `/timezone Europe/Moscow` сохраняет часовую зону IANA; команда без
аргумента показывает текущую настройку. `/why` показывает последнее решение,
выбранный инструмент, ограниченную сводку аргументов, проверку, выполнение и
краткий код причины без скрытых рассуждений модели. В записи аудита PostgreSQL
хранится безопасная ограниченная сводка аргументов; пользовательский текст не
попадает в текстовые журналы.

Перед созданием напоминания бот показывает текст, время, зону и кнопки подтверждения
и отмены. Подтвердить может только владелец в течение 300 секунд. Повторная доставка
того же Telegram-события и повторное нажатие не создают второе действие: подготовка
привязана к событию и позиции вызова, а запись напоминания — к уникальному ключу
идемпотентности. После неопределённого сетевого исхода сервис сверяет результат при
повторе и периодически восстанавливает зависшие `executing` после перезапуска.
Новая попытка не меняет сохранённый текст или время и не продлевает срок подтверждения.

На одно исходное сообщение разрешены не более двух MCP-вызовов; цикл дополнительно
ограничен четырьмя шагами LLM. Плановая доставка уведомлений в заданное время и
проактивная работа с напоминаниями относятся к lab3.

Спецификация контракта: [spec.md](spec.md). Содержательные этапы и критерии
приёмки: [план 04](docs/plans/lab2/04-lab2-implementation.md). Текущие результаты
и оставшиеся проверки: [отчёт lab2](docs/report-lab2.md). Требования курса:
[раздел lab2 методички](docs/labs-guide.md#lab2).

Маршрут сообщения и обязанности методов описаны в
[схеме AgentService](docs/architecture/agent-service.md). `DialogService` владеет
полным запросом и хранением, `ContextBuilder` — памятью и бюджетом,
`AgentService.run` — циклом модели, `ToolExecutionService` — политикой инструментов.
Текущие изменения и критерии: [план 06](docs/plans/lab2/06-agent-reliability-and-weather.md).

Общий `AGENT_TIMEOUT=240` ограничивает обработку после получения места в очереди,
включая metadata, компактизацию, модель и tools. `LLM_TIMEOUT=180` ограничивает одну
генерацию; `LLM_MAX_TOKENS=16384` задаёт лимит вывода (настраивается до 131072),
с резервом не более половины обнаруженного окна контекста. Длинные ответы Telegram
отправляются несколькими сообщениями; незавершённая генерация помечается явно. Summary ограничена
`SUMMARY_MAX_CHARS=2000`, один tool result — `TOOL_RESULT_MAX_CHARS=12000`.
Перед каждым шагом проверяется полный контекст; после чтения tools лимит генерации
уменьшается до оставшегося места в окне, если полный резерв уже не помещается.
Слишком длинный ввод отклоняется
с понятным ответом; JSON результата инструмента не обрезается посередине.

`LLM_STREAMING=true` получает ответ API по SSE, затем SDK собирает полный текст
и аргументы инструментов. Telegram получает готовый результат. Данные reasoning
не выводятся и не логируются. Поток проверяется до завершения: обрыв не превращается
в успешный частичный ответ. Для API без SSE можно задать `LLM_STREAMING=false`.
Повторные метаданные `role=assistant` в SSE нормализуются после сборки SDK;
пропущенная роль определяется как `assistant`. Другие роли продолжают отклоняться.
Исправление метаданных отмечается в логе `llm_stream_role_normalized`.
На внешнем маршруте это уменьшает время без передачи данных; OpenRouter также
отправляет [SSE keep-alive сообщения](https://openrouter.ai/docs/api_reference/streaming).
Общий deadline и таймаут генерации действуют на весь поток, включая ожидание GPU.

При ошибке до инструментов кнопка повтора использует тот же event key и бюджет.
После частично выполненных чтений старый запуск завершается как прерванный:
нужен новый запрос, а промежуточные результаты не восстанавливаются. При старте
одного процесса оставшиеся `processing` помечаются прерванными. Подтверждения имеют
собственное восстановление: `invalid_output` после мутации также требует сверки
с reminder по idempotency key. Повторная доставка предложения учитывает текущее
состояние подтверждения. `dry_run` вызывает LLM, но не пишет БД и не исполняет MCP.

`get_weather(city, date?)` принимает нормальную форму названия: «в Казани» → «Казань».
Явная страна/регион передаётся геокодеру до ограничения выдачи. Дубли одного места
устраняются; единственное точное совпадение предпочтительнее похожих. Среди точных
совпадений город с населением от 100 000 выбирается автоматически, если остальные
меньше 100 000 и ближайший по населению уступает ему минимум в 20 раз. Население
берётся из [ответа геокодера](https://open-meteo.com/en/docs/geocoding-api);
отсутствующее значение считается нулём. Поэтому Казань в Татарстане не требует
выбора между одноимёнными деревнями. Явный регион/страна применяется раньше этого
правила; остальные неоднозначные места требуют уточнения. Город не угадывается
по языку или timezone.
Результат включает текущие условия и `today`: прогноз осадков за весь день в зоне
города (дата, вероятность в %, количество в мм). Дневной максимум не описывает
вероятность дождя прямо сейчас. Для завтра и других дат инструмент получает
дневной прогноз в пределах 16 дней: `requested_date` и `forecast`, содержащий
диапазон температуры, осадки и максимальный ветер. Текущие условия не подменяют
прогноз на будущую дату. При отсутствии нужного прогноза совет не придумывается.
При сетевой недоступности геокодера Open-Meteo используется
[Photon](https://github.com/komoot/photon/blob/master/docs/api-v1.md) с данными
OpenStreetMap; TLS-проверка сохраняется. Одноимённые города требуют уточнения.

Ресурс `schedule://current-week` обнаруживается через MCP и доступен агенту
через адаптер `read_resource` только для обнаруженных разрешённых URI. Это один
вызов в бюджете, а не семь запросов по дням. `get_schedule_week(week_offset=1)`
возвращает следующую неделю по календарю сервера; `get_schedule_week(date)` — неделю,
содержащую дату; `get_schedule(date)` — один день. `data_available=false`
отличает отсутствие данных от свободного дня; `weekday`, `is_free_day` и список
`free_days` вычисляются сервером.

Routing dataset содержит 23 случая, включая нижний регистр, склонения, одежду,
follow-up и отсутствующий город. Dry-run эксперимент измеряет только маршрутизацию
и аргументы. Изолированные проверки полной погодной цепочки отдельно проверяют
геокодирование, дату/единицы прогноза и ответ; они не доказывают качество живой LLM.

### Подготовка SDK, промптов и Telegram

Предварительные изменения описаны в
[плане 05](docs/plans/lab2/05-llm-sdk-prompts-and-telegram.md). Историческая
сводка этих проверок находится в самом плане.

Ограничения выбранной библиотеки: один завершающий перенос fenced-блока убирается,
пустые/пробельные части не отправляются; при жёстком разбиении очень длинной строки
составной emoji может попасть в разные сообщения. UTF-16 surrogate pairs и порядок
оставшихся символов сохраняются. Формулы следует писать текстом или code: флаг
`latex_escape=False` отключает преобразование скобочной LaTeX-записи, но собственный
синтаксис библиотеки `$...$` всё ещё обрабатывается как математическая разметка.

Для оценки маршрутизации используйте `uv run --locked python -m
scripts.run_routing_eval --live --label baseline`. После изменения можно
запустить выбранные случаи, например:

```bash
uv run --locked python -m scripts.run_routing_eval --live --label after-change --cases weather_1 schedule_1
```

`--live` обращается к настроенному LLM API; учитывайте стоимость и доступность
провайдера. Отчёт различает полученные решения и не запущенные случаи: нулевые
оценки при отсутствии решений не измеряют качество модели.
