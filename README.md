# Telegram-бот «AI-ассистент студента»

Асинхронный Telegram-бот на базе Python 3.12 и aiogram 3, интегрированный с большими языковыми моделями (LLM) через OpenAI-совместимый API и СУБД PostgreSQL для сохранения контекста диалога, выжимок истории и настроек пользователей.

---

## 1. Стек технологий и инструменты

- **Язык и среда:** Python 3.12
- **Пакетный менеджер и виртуальное окружение:** [uv](https://github.com/astral-sh/uv)
- **Telegram фреймворк:** [aiogram 3](https://docs.aiogram.dev/) (асинхронный long polling, роутеры, фильтры, inline-клавиатуры)
- **СУБД и пул соединений:** PostgreSQL 16 (в Docker Compose), асинхронный драйвер `asyncpg` с пулом подключений
- **Миграции базы данных:** собственный асинхронный runner с `pg_advisory_lock` и контрольными суммами SHA-256 (`app/db/migrations/`)
- **LLM-интеграция:** `openai.AsyncOpenAI` (Chat Completions через HTTPX2; настраиваемый OpenAI-совместимый endpoint)
- **MCP:** FastMCP 4.1.5; отдельные серверы `student-tools` и `math-tools` на FastMCP, составной клиент и FastMCP Client в приложении, транспорты `stdio` и Streamable HTTP
- **Схемы и валидация данных:** `pydantic v2` (модели запросов/ответов LLM, сообщений, валидация настроек пользователей)
- **Форматирование Telegram:** `telegramify-markdown==1.4.1` (текст + entities, готовое разбиение)
- **Служебный HTTP-сервер:** `aiohttp` (эндпоинт `/health` на порту 8080 для Docker и оркестраторов)
- **Контейнеризация:** Docker, Docker Compose
- **Проверки:** `pytest`, `pytest-asyncio`, `ruff`, `ty`; управление окружением через `uv`

## 2. Принцип работы бота

### Схема обработки запроса пользователя
1. **Приём апдейта:** Пользователь отправляет сообщение в Telegram. `aiogram` направляет его в роутер диалога (`app/handlers/dialog.py`).
2. **Трассировка и UX:** Генерируется уникальный `request_id` (передаётся через `contextvars`), в чат отправляется статус набора текста (`chat_action="typing"`).
3. **Обработка запроса:**
   - `DialogService` сериализует запросы пользователя и проверяет event key до подготовки контекста. Повтор возвращает сохранённый результат без LLM и новых реплик; технический статус обработки не попадает в память.
   - `ContextBuilder` собирает RCTF-инструкции режима, summary, целые пары реплик и проверенный статус последнего подтверждения. История, summary и результаты tools остаются данными, а не новыми системными инструкциями.
   - Metadata размера окна определяется отдельно от генерации и кэшируется по модели/endpoint; для неизвестного провайдера используется `DEFAULT_CONTEXT_LENGTH`. Общий бюджет консервативно оценивает UTF-8 размер сообщений и схем, учитывая резерв вывода; это не точный токенизатор произвольной модели.
   - При компактизации выбирается ограниченная порция старых полных пар. Новая summary и удаление исходных сообщений сохраняются одной транзакцией. `COMPACTION_KEEP_RECENT=3` округляется вверх до четырёх реплик, чтобы сохранить целые пары.
   - `AgentService` выполняет один обычный цикл tool calling и формирует определения локальных функций чтения обнаруженных ресурсов и уточнения. `ToolExecutionService` валидирует весь пакет вызовов, выполняет MCP tools и перехватывает чтение ресурса на стороне приложения; оно не отправляется как `tools/call` на MCP-сервер.
   - Итог события, обе реплики и продуктовый аудит сохраняются атомарно. Сетевые вызовы не удерживают SQL-транзакции. SDK-клиенты живут до остановки приложения; неявные SDK retries отключены.
4. **Рендеринг и чанкинг:**
   - Полный Markdown один раз проходит `telegramify_markdown.convert(latex_escape=False)` с изолированной конфигурацией без emoji у заголовков/ссылок и с маркером списка `-`. Затем `split_entities(..., max_utf16_len=4096)` делит текст и entities; отправка через aiogram всегда использует `parse_mode=None`.
   - Обёртка проверяет UTF-16 offsets, допускает bold/italic/code/pre/text_link и ссылки HTTP(S). Неизвестные entities удаляются с сохранением видимого текста. Собственных парсера, HTML-рендера и splitter нет.
   - При сбое конвертации отправляется исходный текст без entities; при отказе Telegram из-за entities — видимый текст только отклонённой части. Оба plain-text пути также используют `split_entities`; сетевые и остальные API-ошибки не повторяются. Reply-to ставится на первый фрагмент, inline-кнопки — на последний. Пустой результат не отправляется.

### Режимы работы (роли)
- `/study` — **«Обучение»:** ментор студента ИТМО по математике, алгоритмам и ПО. Обосновывает решение, учитывает уровень и нужный язык; код приводит по задаче, по просьбе о подсказке не раскрывает полное решение.
- `/translate` — **«Переводчик»:** математический и технический перевод текстов, документации и кода с сохранением синтаксиса и терминологии.
- `/review` — **«Код-ревью»:** ревью кода с few-shot примерами. Анализирует найденные проблемы, оценивает алгоритмическую сложность (Big O) и предлагает улучшенный вариант реализации.
- `/everyday` — **«Повседневный помощник»** для бытовых дел, погоды, напоминаний и общих вопросов.

Роль задаёт инструкции модели. Каталог MCP-инструментов и ресурсов общий для всех ролей.

### Команды бота
- `/start` — приветственное сообщение и интерактивный выбор роли через inline-кнопки.
- `/help` — список доступных ролей и команд бота.
- `/study`, `/translate`, `/review` — быстрое переключение активной роли.
- `/settings` — интерактивный выбор температуры генерации (`0.0`, `0.3`, `0.7`, `1.0`) через inline-кнопки.
- `/reset` — атомарная очистка сообщений и summary. Сохранённые подтверждения остаются действующими; их payload и timezone не меняются задним числом.

### Описание бота

При каждом запуске бот через aiogram обновляет описание в пустом чате и краткое
описание профиля. Тексты находятся в `BOT_DESCRIPTION` и `BOT_SHORT_DESCRIPTION`
в `app/telegram.py`; они задаются для языка по умолчанию. Изменения через
BotFather `/setdescription` и `/setabouttext` для этого языка будут перезаписаны
при следующем запуске. Ошибка обновления описания записывается в лог и не мешает
боту запуститься.

### Отказоустойчивость
- **Таймауты LLM:** при превышении времени ожидания (`LLM_TIMEOUT`, по умолчанию 180 с) бот отправляет сообщение об ошибке с inline-кнопкой «🔄 Повторить».
- **Причины ошибок LLM:** бот различает ошибки ключа и прав доступа, адреса или модели, квоты, соединения, параметров запроса, формата ответа и лимита генерации. `/why` показывает понятное объяснение вместо `llm_error`. Логи `llm_start`, `llm_usage` и `llm_complete` содержат имя модели; `llm_failed` и `llm_error` — код причины, HTTP-статус и безопасную диагностику. Для ошибок формата сохраняются этап (`request_payload`, `response_decode`, `stream_decode`, `response_validation`, `tool_arguments`), тип исключения, место ошибки в коде, путь поля и причина проверки либо строка/столбец некорректного JSON. Ошибка провайдера внутри SSE сохраняет известный код и распознанную причину и не выдаётся за ошибку формата. Тексты запросов, ответы провайдера и содержимое исключений в диагностические логи не попадают.
- **Маскирование секретов:** фильтр `SecretFilter` автоматически скрывает токен бота, ключ LLM, пароли БД и параметры прокси из логов и трейсбеков.
- **Healthcheck:** HTTP-эндпоинт отдаёт `200 OK` только при одновременной доступности Telegram polling и успешном выполнении `SELECT 1` в PostgreSQL.

## 4. Конфигурация (`config.toml` и `.env`)

Версионируемый `config.toml` задаёт безопасный профиль по умолчанию. Секреты,
токены, пароли и прокси с учётными данными хранятся только в `.env` или
окружении процесса: загрузчик отклоняет неизвестные параметры и учётные данные
в публичных URL. Приоритет от низшего к высшему: значения кода, `config.toml`,
`.env`, окружение процесса. Пустое значение считается незаданным и передаёт
приоритет следующему непустому источнику. Для контейнеров Compose встроенный
`config.toml` используется по умолчанию; отдельные профили подключаются через
`compose.config.yaml`:

```bash
BOT_CONFIG_FILE=./config.bot.toml \
MATH_MCP_CONFIG_FILE=./config.math.toml \
docker compose -f compose.yaml -f compose.config.yaml --profile cloud up -d
```

Секции `config.toml` — `[llm]`, `[agent]`, `[history]`, `[mcp]` и `[math_mcp]`.
Типы, диапазоны и неизвестные ключи проверяются с указанием секции и параметра.
Диагностический метод `Settings.diagnostics()` показывает эффективные значения
без токенов, паролей, секретов и прокси. Профиль OpenCode Go с окном 131072 и
потолком ответа 32768 задаётся в `.env` развёрнутого сервера, а базовый
`config.toml` сохраняет прежний OpenRouter-профиль.

Создайте файл `.env` в корне проекта на основе `.env.example`. В шаблоне
активны только секреты и параметры запуска, а несекретные настройки оставлены
комментариями: их базовые значения уже есть в `config.toml`.

```dotenv
# Telegram
BOT_TOKEN=123456789:ABCDEF...
TELEGRAM_PROXY_URL=              # Опционально: http://user:pass@host:port или socks5://host:port

# PostgreSQL
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DB=bot
POSTGRES_USER=bot
POSTGRES_PASSWORD=secret_password

# LLM
LLM_API_KEY=sk-or-v1-...

# MCP, для Streamable HTTP нужен общий секрет не короче 32 символов
MCP_SHARED_SECRET=
```

### Тестовый режим OpenCode Go

Для проверки через OpenCode Go оставьте обычные `LLM_*` и включите
дополнительные заголовки одной строкой:

```dotenv
LLM_API_KEY=<ключ OpenCode Go>
LLM_BASE_URL=https://opencode.ai/inference/go/openai/v1
LLM_MODEL=deepseek-v4.1-flash
LLM_OPENCODE_SESSION=1
DEFAULT_CONTEXT_LENGTH=131072
LLM_MAX_TOKENS=32768
LLM_GENERATION_RESERVE_TOKENS=4096
```

При `LLM_OPENCODE_SESSION=1` клиент отправляет `User-Agent: itmo-study-bot/0.1`
и стабильный для времени жизни процесса заголовок
`x-opencode-session: ses_<uuid4>`. Сессия создаётся на клиент и не содержит
Telegram ID: это режим однопользовательской проверки API, а не
многопользовательской изоляции. При `0` (по умолчанию) заголовки и запросы
не меняются. После изменения `.env` перезапустите бота; новый процесс начнёт
новую сессию.

## 5. Запуск проекта

### Вариант 1: Запуск через `uv` (рекомендуемый)

1. **Установите `uv`** (если ещё не установлен):
   ```bash
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

2. **Подготовьте окружение:**
   ```bash
   uv sync --locked
   ```
   Python 3.12 выбирается из `.python-version`; при необходимости uv загрузит его.

3. **Запустите PostgreSQL в Docker:**
   ```bash
   docker compose -f compose.yaml -f compose.local.yaml up -d db
   ```

4. **Запустите бота:**
   ```bash
   uv run --locked python -m app
   ```

`uv` создаёт `.venv` и устанавливает зависимости по `uv.lock`. Миграции PostgreSQL
применяет само приложение при запуске перед началом long polling.

Зависимости объявлены в `pyproject.toml`, точные версии зафиксированы в `uv.lock`.

## Lab 2: MCP-агент

Lab2 расширяет этого бота инструментами FastMCP. Сервер `student_tools` публикует
`get_weather`, `get_schedule`, `get_schedule_week`, `add_reminder` и ресурс
`schedule://current-week`. Независимый сервер `math_tools` публикует
`math_calculate`, `math_solve` и `math_plot`. Клиент получает их входные и
выходные схемы через discovery, проверяет аргументы и структуру результатов.
Погода запрашивается у Open-Meteo, расписание загружается из JSON-файла,
напоминания и подтверждения хранятся в PostgreSQL. Математический сервер не
зависит от базы, Telegram или LLM.

Один составной клиент объединяет discovery доступных серверов. Инструменты и
ресурсы с совпадающими именами или URI исключаются из общего каталога и
отклоняются при прямом вызове; каталог и валидаторы принадлежат исходному
клиенту. Если один сервер недоступен, второй продолжает работать, а фоновый
цикл повторяет discovery только недоступного сервера. Подтверждение напоминания
всегда отправляется в `student_tools`.

Локально по умолчанию используется `stdio`: бот запускает оба MCP-сервера как
дочерние процессы, поэтому отдельный порт и отдельная команда запуска серверов
не нужны. Сервер `student_tools` получает отдельное окружение без Telegram- и
LLM-секретов; `math_tools` получает общие переменные окружения, разрешённые
переопределения `MATH_MCP_*` и `MCP_SHARED_SECRET`. Для HTTP используется
Streamable HTTP; бот подключается к `/mcp/` с `Authorization: Bearer`.
Compose service для `student_tools` называется `student-tools-mcp`, для
математики — `math-tools-mcp`. Внутри сети Compose бот обращается к
`http://student-tools-mcp:8000/mcp` и `http://math-tools-mcp:8000/mcp`.
FastMCP server names — `student-tools` и `math-tools`. Оба сервера слушают
внутреннюю сеть Compose и не публикуют порт наружу. Для этого режима задайте
один и тот же `MCP_SHARED_SECRET` длиной не менее 32 символов в окружении бота
и обоих серверов. Пустой `MATH_MCP_SERVER_URL` сохраняет прежний режим с одним
сервером `student_tools`. В режиме `stdio`, если секрет не задан, клиент создаёт
временный секрет для запуска дочерних процессов.

Для локального запуска FastMCP-сервера отдельно (например, для MCP Inspector)
подготовьте `.env` с `MCP_SHARED_SECRET` длиной не менее 32 символов; для
`student_tools` также нужны PostgreSQL-параметры. Не вставляйте реальный секрет
в документацию, скриншоты или отчёт. Затем запускайте нужный транспорт:

```bash
uv run --locked python -m mcp_servers.student_tools --transport stdio --env-file .env
uv run --locked python -m mcp_servers.student_tools --transport streamable-http --env-file .env
uv run --locked python -m mcp_servers.math_tools --transport stdio --env-file .env
uv run --locked python -m mcp_servers.math_tools --transport streamable-http --env-file .env
```

`math_tools` не читает PostgreSQL, Telegram или LLM-настройки. Для Streamable
HTTP ему нужны `MCP_HOST` (по умолчанию `0.0.0.0`), `MCP_PORT` (по умолчанию
`8000`) и общий `MCP_SHARED_SECRET`; проверка готовности — `GET /health` или
`uv run --locked python -m mcp_servers.math_tools.healthcheck`. Чтобы запустить
оба HTTP-сервера одновременно, назначьте им разные `MCP_PORT`.

Для Inspector 2.12 настройте stdio-сервер командой `uv` и аргументами
`run --locked python -m mcp_servers.student_tools --transport stdio --env-file .env`,
передав PostgreSQL-переменные и общий `MCP_SHARED_SECRET` в окружение процесса.
Для `math_tools` используйте команду с `mcp_servers.math_tools`. Для Streamable
HTTP укажите URL `http://127.0.0.1:8000/mcp/` и заголовок
`Authorization: Bearer <MCP_SHARED_SECRET>`; секрет должен совпадать с серверным.
Используйте отдельную тестовую базу и тестовую учётную запись, особенно при
проверке изменения данных.

### Математические инструменты

`math_calculate` возвращает точные и численные результаты SymPy, в том числе
производные, пределы, интегралы, сходимость рядов, матрицу Якоби и кандидатов
на условные экстремумы. `math_solve` решает системы до трёх уравнений и
проверяет решения подстановкой и по области определения.

`math_plot` строит обычные и параметрические кривые, линии уровня,
вещественные поверхности, цветовые карты комплексных функций и 3D-графики
их модуля. Описание графика и контрольные точки идут в `structuredContent`,
PNG — в `ImageContent`. Например, запрос «Построй цветовую карту `1/z` на
квадрате от −2 до 2 по обеим осям» выбирает `plot_type=domain_coloring`.
Сложные задачи и команды воспроизведения собраны в
[отчёте по MathMCP](docs/evaluation/plan10/README.md).

Выражения собираются из разрешённых узлов AST: числа, переменные, скобки,
явное умножение, `**` и `^`, базовые математические функции. Длина выражения
ограничена 512 символами, дерево — 128 узлами; `eval`, `sympify` и `parse_expr`
не используются. На сервере выполняется один активный расчёт, лимит операции —
5 секунд и 768 МиБ памяти; при тайм-ауте процесс завершается. PNG ограничен
256 КиБ на изображение. Эти значения заданы в секции `[math_mcp]` файла
`config.toml` и не могут превышать действующий контракт PNG; окружение процесса
переопределяет их через `MATH_MCP_OPERATION_TIMEOUT_SECONDS`,
`MATH_MCP_STARTUP_TIMEOUT_SECONDS`, `MATH_MCP_QUEUE_TIMEOUT_SECONDS`,
`MATH_MCP_MEMORY_LIMIT_MIB` и `MATH_MCP_MAX_PNG_BYTES`. Клиент бота ждёт MathMCP
до `MATH_MCP_REQUEST_TIMEOUT_SECONDS` (по умолчанию 40 секунд), тогда как
обычный MCP ограничен `MCP_TIMEOUT=10`. Модель получает только структурированный
текст, а изображения передаются отдельно. По умолчанию бюджет составляет пять
MCP-вызовов на сообщение и четыре шага LLM.

В облачном сценарии скрипт развёртывания сам создаёт и сохраняет ключ MCP;
при ручном запуске Compose задайте общий `MCP_SHARED_SECRET` в локальном `.env`.
После этого выполните:

```bash
docker compose --profile cloud up --build -d
```

Команда `/tools` показывает только обнаруженные возможности и помечает чтение и
изменение. `/timezone Europe/Moscow` сохраняет часовую зону IANA; команда без
аргумента показывает используемую зону. По умолчанию применяется `Europe/Moscow`;
явно сохранённая пользователем зона имеет приоритет. `/why` показывает последнее решение,
выбранный инструмент, использованные ресурсы, ограниченную сводку аргументов,
проверку, выполнение и понятное объяснение причины без скрытых рассуждений модели. В записи аудита PostgreSQL
хранится безопасная ограниченная сводка аргументов; пользовательский текст не
попадает в текстовые журналы.

Перед созданием напоминания бот показывает текст, время, зону и кнопки подтверждения
и отмены. Подтвердить может только владелец в течение 300 секунд. Повторная доставка
того же Telegram-события и повторное нажатие не создают второе действие: подготовка
привязана к событию и позиции вызова, а запись напоминания — к уникальному ключу
идемпотентности. После неопределённого сетевого исхода сервис сверяет результат при
повторе и периодически восстанавливает зависшие `executing` после перезапуска.
Новая попытка не меняет сохранённый текст или время и не продлевает срок подтверждения.

Лимит `AGENT_MAX_TOOL_CALLS` задаёт общий бюджет исходного сообщения: вызовы
инструментов и ресурсов, исполнение подтверждения и его повторные попытки.
По умолчанию лимит равен пяти. Число шагов модели задаётся отдельно через
`AGENT_MAX_LLM_STEPS` и по умолчанию равно четырём. Плановая доставка уведомлений в заданное время и
проактивная работа с напоминаниями относятся к lab3.

для защиты описаны в [путеводителе по кодовой базе](docs/architecture/overview.md).
Маршрут сообщения и обязанности методов описаны в
[схеме AgentService](docs/architecture/agent-service.md). Реализация упрощения клиента,

Надёжность и погода описаны в [плане 06](docs/plans/lab2/06-agent-reliability-and-weather.md),
последующее упрощение MCP-клиента — в [плане 07](docs/plans/lab2/07-post-lab2-simplification.md).

Общий `AGENT_TIMEOUT=240` ограничивает обработку после получения места в очереди,
включая metadata, компактизацию, модель и tools. `LLM_TIMEOUT=180` ограничивает одну
генерацию; `LLM_MAX_TOKENS=16384` задаёт лимит вывода (настраивается до 131072),
а `LLM_GENERATION_RESERVE_TOKENS=4096` — целевой резерв под текущий ответ, который
не превышает фактический лимит вывода и половину обнаруженного окна контекста.
Длинные ответы Telegram
отправляются несколькими сообщениями; незавершённая генерация помечается явно. Summary ограничена
`SUMMARY_MAX_CHARS=2000`, один tool result — `TOOL_RESULT_MAX_CHARS=12000`.
Перед каждым шагом проверяется полный контекст. Если базовый запрос со схемами
помещается, но полный резерв ответа уже не входит, лимит генерации уменьшается
до оставшегося места; это действует и до первого шага, и после чтения tools.
Для генерации должно оставаться не менее 64 токенов.
При подготовке запроса свежая история имеет приоритет над максимальным резервом
ответа: сначала сохраняются помещающиеся целые пары реплик, затем оставшееся место
выделяется генерации. При нехватке окна отбрасываются самые старые пары.
Слишком длинный ввод отклоняется
с понятным ответом; JSON результата инструмента не обрезается посередине.

Для оплаченного API с большим окном можно использовать более свободный рабочий
профиль, сохранив локальное ограничение вместо полного окна модели:

```dotenv
LLM_CONTEXT_PROVIDER=none
DEFAULT_CONTEXT_LENGTH=131072
LLM_MAX_TOKENS=16384
HISTORY_MAX_MESSAGES=60
HISTORY_MAX_CHARS=40000
COMPACTION_THRESHOLD_MESSAGES=60
COMPACTION_KEEP_RECENT=20
SUMMARY_MAX_CHARS=4000
```

При `LLM_CONTEXT_PROVIDER=none` приложение использует заданное окно без обращения
к каталогу моделей. Это ограничение по текущей консервативной оценке размера
запроса, а не измеренные токены провайдера. Настройки сохраняют до 30 последних
пар реплик в пределах 40 тысяч символов; при сжатии последние 10 пар остаются
дословно. Максимальная длина ответа задаётся отдельно. После изменения `.env`
нужно перезапустить бот; на развёрнутом сервере профиль применяется в его окружении.

Окно контекста модели и квота провайдера — разные ограничения. Например,
Groq отдельно ограничивает запросы и токены за минуту или день;
точные значения доступны в [Limits](https://console.groq.com/settings/limits),
а смысл ограничений описан в [документации Groq](https://console.groq.com/docs/rate-limits).
При HTTP 429 логи сохраняют распознанный тип квоты (`TPM`, `TPD`, `RPM`, `RPD`)
и доступные числовые заголовки: лимиты, остатки, время сброса и `retry_after_seconds`.
Произвольные значения заголовков и полный текст ошибки провайдера не выводятся.
Увеличение тайм-аута не снимает ограничение квоты.

`LLM_STREAMING=true` получает ответ API по SSE, затем SDK собирает полный текст
и аргументы инструментов. Telegram получает готовый результат. Данные reasoning
не выводятся и не логируются. Поток проверяется до завершения: обрыв не превращается
в успешный частичный ответ. Для API без SSE можно задать `LLM_STREAMING=false`.
Повторные метаданные `role=assistant` в SSE нормализуются после сборки SDK;
пропущенная роль определяется как `assistant`. Другие роли продолжают отклоняться.
Исправление метаданных отмечается в логе `llm_stream_role_normalized`.
На внешнем маршруте это уменьшает время без передачи данных; OpenRouter также
отправляет [SSE keep-alive сообщения](https://openrouter.ai/docs/api_reference/streaming).
Общий deadline и таймаут генерации действуют на весь поток, включая ожидание GPU.

При ошибке до инструментов кнопка повтора использует тот же event key и бюджет.
После частично выполненных чтений старый запуск завершается как прерванный:
нужен новый запрос, а промежуточные результаты не восстанавливаются. При старте
одного процесса оставшиеся `processing` помечаются прерванными. Подтверждения имеют
собственное восстановление: `invalid_output` после мутации также требует сверки
с reminder по idempotency key. Повторная доставка предложения учитывает текущее
состояние подтверждения. Автоматических повторов MCP-вызова после ошибки клиента нет.
`MCPClient` открывает SDK-контекст на каждую операцию; RPC timeout не сбрасывает
discovery-каталог и не закрывает другие активные запросы. `__main__` периодически
повторяет discovery, когда каталог помечен недоступным; уже отправленный RPC не
переигрывается.

`get_weather(city?, date?)` принимает нормальную форму названия: «в Казани» → «Казань».
Без города по умолчанию используется Санкт-Петербург; в продолжении диалога агент
может использовать ранее явно названный город. Без даты погода запрашивается на сегодня
в часовом поясе города. `get_schedule(date?)` без даты возвращает сегодняшний день
в `SCHEDULE_TIMEZONE`. Поэтому «Какая погода?» и «Покажи расписание» не требуют
уточнения города и даты. Явные город, дата и период имеют приоритет над значениями по умолчанию.
Явная страна/регион передаётся геокодеру до ограничения выдачи. Дубли одного места
устраняются; единственное точное совпадение предпочтительнее похожих. Среди точных
совпадений город с населением от 100 000 выбирается автоматически, если остальные
меньше 100 000 и ближайший по населению уступает ему минимум в 20 раз. Население
берётся из [ответа геокодера](https://open-meteo.com/en/docs/geocoding-api);
отсутствующее значение считается нулём. Поэтому Казань в Татарстане не требует
выбора между одноимёнными деревнями. Явный регион/страна применяется раньше этого
правила; остальные неоднозначные места требуют уточнения. Город не угадывается
по языку или timezone.
Результат включает текущие условия и `today`: прогноз осадков за весь день в зоне
города (дата, вероятность в %, количество в мм). Дневной максимум не описывает
вероятность дождя прямо сейчас. Для завтра и других дат инструмент получает
дневной прогноз в пределах 16 дней: `requested_date` и `forecast`, содержащий
диапазон температуры, осадки и максимальный ветер. Текущие условия не подменяют
прогноз на будущую дату. При отсутствии нужного прогноза совет не придумывается.
При сетевой недоступности геокодера Open-Meteo используется
[Photon](https://github.com/komoot/photon/blob/master/docs/api-v1.md) с данными
OpenStreetMap; TLS-проверка сохраняется. Если неоднозначность осталась после
фильтрации, бот просит уточнить место.

Ресурс `schedule://current-week` обнаруживается через MCP и доступен модели как
локальная функция `read_resource(uri)`. Список URI в её схеме строится из discovery
и проверяется приложением до чтения. Это функция-host-adapter: агент не вызывает её
через MCP `tools/call`, а сервер не публикует ресурс в `tools/list`. Хост читает URI
через FastMCP Client `read_resource()`, затем возвращает результат в сообщение роли
`tool` с исходным `tool_call_id` и JSON-обёрткой `source`, `uri`, `mime_type`, `content`.
Данные и обёртка недоверенны. Ошибка самого resource RPC возвращается модели как
tool error content; приложение не повторяет RPC автоматически, а модель может
продолжить с уточнением или ответом без недоступных данных. Ошибки URI/аргументов,
бюджета и нативных MCP tools остаются терминальными. Каждый ресурсный RPC расходует
один вызов из общего лимита `AGENT_MAX_TOOL_CALLS`. Инструменты и ресурсы
используют один агентный цикл с отдельным лимитом шагов LLM. Успешные URI попадают в `AgentResult`, JSONB
аудита и `/why`. `get_schedule_week(week_offset=1)`
возвращает следующую неделю по календарю сервера; `get_schedule_week(date)` — неделю,
содержащую дату; `get_schedule(date)` — один день. `data_available=false`
отличает отсутствие данных от свободного дня; `weekday`, `is_free_day` и список
`free_days` вычисляются сервером.

В репозитории находится вымышленное расписание на **2–29 сентября 2030 года**:
`mcp_servers/student_tools/data/schedule.json`. За пределами этого периода сервер честно сообщает об
отсутствии данных. Личное расписание храните в `.local/schedule.json` и задайте
`SCHEDULE_PATH=.local/schedule.json` в локальном `.env`. Каталог `.local/`
игнорируется Git и не попадает в образ или архив исходников. При создании удалённого
`.env.cloud` deploy заменяет только `SCHEDULE_PATH`, содержащий сегмент `.local`,
на упакованное демонстрационное расписание; локальный `.env` не меняется. Другие
пользовательские пути сохраняются, и относительный путь разрешается от каталога
проекта на сервере. Compose подключает выбранный файл в MCP-сервер только для чтения;
в контейнере его целевой путь — `mcp_servers/student_tools/data/schedule.json`.

`DialogService` координирует запрос и обращается к `ConfirmationService` напрямую,
а каталог `/tools` и ресурсы получает через `ToolClient`. Исполнение чтений и подготовка
действий остаются в `ToolExecutionService`. Внутренний `StepAction.CONTINUE`
продолжает цикл после чтения; приложение предоставляет локальный инструмент
`clarification(question)` для уточняющего вопроса без MCP-вызова. `/why` показывает
выбранные ресурсы отдельно от инструментов и объясняет решение без вызова LLM.

Основной routing dataset сохраняет 12 исходных случаев lab2. Ещё 11 сценариев
вынесены в `docs/evaluation/lab2-routing-extended.json`: нижний регистр, склонения,
одежда, follow-up, периоды и город по умолчанию. Оценка маршрутизации измеряет только маршрутизацию
и аргументы. Изолированные проверки полной погодной цепочки отдельно проверяют
геокодирование, дату/единицы прогноза и ответ; они не доказывают качество живой LLM.

### Подготовка SDK, промптов и Telegram

Предварительные изменения описаны в
[плане 05](docs/plans/lab2/05-llm-sdk-prompts-and-telegram.md). Историческая
сводка этих проверок находится в самом плане.

Ограничения выбранной библиотеки: один завершающий перенос fenced-блока убирается,
пустые/пробельные части не отправляются; при жёстком разбиении очень длинной строки
составной emoji может попасть в разные сообщения. UTF-16 surrogate pairs и порядок
оставшихся символов сохраняются. Формулы следует писать текстом или code: флаг
`latex_escape=False` отключает преобразование скобочной LaTeX-записи, но собственный
синтаксис библиотеки `$...$` всё ещё обрабатывается как математическая разметка.

Для оценки маршрутизации используйте `uv run --locked python -m
scripts.run_routing_eval --live --label baseline`. После изменения можно
запустить выбранные случаи, например:

```bash
uv run --locked python -m scripts.run_routing_eval --live --label after-change --cases weather_1 schedule_1
uv run --locked python -m scripts.run_routing_eval --live --label extended --dataset docs/evaluation/lab2-routing-extended.json
```

`--live` обращается к настроенному LLM API; учитывайте стоимость и доступность
провайдера. Отчёт различает полученные решения и не запущенные случаи: нулевые
оценки при отсутствии решений не измеряют качество модели.
Для сравнения аргументов оценщик применяет одинаковые значения по умолчанию к
ожиданию и решению модели. Пропуск даты равнозначен сегодняшней дате из frozen clock,
пропуск города — Санкт-Петербургу; будущая дата, другой город и лишние поля по-прежнему
проверяются. JSON сохраняет исходные и эффективные аргументы, имя и SHA-256 набора,
SHA-256 оценщика и исходников приложения.
